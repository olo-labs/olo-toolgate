# Documentation Style Guide

## Goal

A contributor should understand a document in one pass.

## Rules

- Start every file with **Purpose**.
- State **must/should/may** rules explicitly.
- Prefer diagrams and concrete examples over abstract prose.
- Put security invariants in callouts or dedicated sections.
- Link to the next useful document.
- Do not duplicate large sections from the master specs.
- Keep API examples executable-looking and consistent with canonical schemas.
- Never place real credentials in examples.

## File Pattern

```text
# Title

## Purpose
## Architecture / Flow
## Rules
## Configuration
## Failure Behavior
## Testing
## Related Docs
```
